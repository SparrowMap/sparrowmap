Node hardware

What a camera node actually costs in compute, what a Raspberry Pi really does with it, and how to measure your own board so the answer stops being an opinion.

The short version

The detector you run matters about eleven times more than the board you buy. That was measured, not guessed, and it is the opposite of how the question is usually asked. Pick the model first, then the hardware.

A Pi 5 runs a full node. A Pi 4 runs a detect-and-ship node. A Pi Zero does not run one at all. All three of those statements have a caveat, and they are below.

A node is three workloads, not one

Most of the confusion about hardware comes from treating "run a SparrowMap node" as a single thing. It is three, and they have wildly different appetites. A board can pass the first two and fail the third and still be a genuinely useful node.

1 · Vehicle detection

Finds vehicles in the frame and tracks them across it. ONNX, no torch. This is the one that runs constantly, so it sets your frame rate.

rf-detr-small-512 · runs anywhere · the expensive one

2 · Plate read

Localises the plate inside a vehicle box and reads it. ONNX, no torch. Only runs when a vehicle was found, so its cost scales with traffic rather than with time.

yolo-v9-s-608 + cct-s-v2 · runs anywhere

3 · The government call

Decides patrol car versus ordinary car. Needs CLIP and a trained head, which means torch, which means about 2.5 GB installed. This is the tier a small board skips.

CLIP ViT-B/32 + head · needs torch

Leave out tier three and the node still runs. It still reports vehicles and still reads plates; it simply treats every vehicle as civilian and lets a hub or a desktop node make the government call. That is not a degraded node, it is the same split the browser camera already uses.

What was actually measured

Median inference time per call, CPU only, on an i9-9900K (8 cores / 16 threads). The four-thread column is there because a Pi has four cores, so it is the honest structural comparison — not the sixteen-thread number a desktop would quote.

ModelStage1 thread24 threads8
rf-detr-small-512vehicle detect 649 ms379250 ms210
yolo-v9-s-608plate box 267 ms15298 ms92
yolo11s @320vehicle detect (browser path) 66 ms3423 ms24

Two things fall out of that table, and both are more useful than a shopping recommendation.

The heavy detector barely scales. rf-detr goes from 649 ms on one thread to 210 ms on eight — a factor of three from eight times the cores. Throwing cores at it does not rescue it, which is why "just get more cores" is the wrong lever here.

The light detector is eleven times cheaper. Same box, same conditions: 649 ms against 66 ms single-threaded. That is a bigger gap than exists between any two boards you might be choosing between, and it is a software choice rather than a purchase.

End to end, the whole Python pipeline on that box measures 240 ms per frame, about 4.2 detections per second, with the detector on CPU. That is the anchor every estimate below is scaled from.

Why the Zero is a flat no

The Zero 2 W fails on memory, not speed. 512 MB has to hold three ONNX sessions, OpenCV, and a frame buffer at the same time. Slow would be survivable at a low duty cycle; running out of RAM is not something you can tune around. The original Zero and Zero W fail earlier still — they are ARMv6, and onnxruntime does not ship wheels for ARMv6 at all, so there is nothing to install.

What the "light detector" row assumes

Honesty about scope: yolo11s is not a configuration flag on a Python node today. It is the model the in-browser camera already uses, it is already in this repo at public/vendor/yolo11s.onnx, and the measurement above says it would transform Pi-class performance — but wiring it into the Python detector is a change to the code, not a setting you pass. If you are experimenting on a Pi, that is probably the most valuable thing you could contribute.

How to test your own board

Everything above is a prediction until somebody runs it. The benchmark is in the repo and needs no camera, no test footage and no hub — it generates its own deterministic frame so that two people on two continents produce comparable numbers.

git clone https://github.com/SparrowMap/sparrowmap
cd sparrowmap
pip install -r requirements-node.txt   # or omit torch; see below

# the standard run — this is the one to report
python tools/bench_node.py --label "Pi 5 8GB, active cooler"

# a proper thermal soak, ten minutes
python tools/bench_node.py --seconds 600 --label "Pi 5 8GB, no cooler"

# time it against a real road photo instead of the synthetic frame
python tools/bench_node.py --image myshot.jpg

# also check the camera can actually feed it
python tools/bench_node.py --camera 0

It prints a verdict and a single JSON line. Paste the JSON line — it carries the board model, core count, RAM, onnxruntime version, per-stage medians and the thermal drift, which is everything needed to compare two results without a conversation.

What the benchmark deliberately does

  • Times the three stages separately, because "it is too slow" and "torch will not install" are different problems with the same symptom.
  • Warms up before timing. The first ONNX run allocates arenas and is not representative of anything.
  • Reports medians, not means. One background job on a small board wrecks a mean.
  • Soaks for minutes and reports first-versus-last. A passively cooled board holds full clocks for about a minute, so a burst benchmark reports a number the machine cannot sustain for an afternoon — and an afternoon is the only duration that matters for a camera in a window.
  • Reads the SoC's own throttle flags via vcgencmd get_throttled, including the latched-since-boot bits. A latched under-voltage flag is the single most common cause of a Pi that "runs slow", and it is a power supply, not software.
  • Treats missing torch as a tier, not a failure. That is the expected result on a small board.

It measures speed, not accuracy

CNN inference cost is set by input size, not by picture content, so the synthetic frame gives a comparable timing on a machine with no test data. Detection accuracy on that frame is meaningless and the script does not report it. Do not quote it as a quality number.

The configuration worth starting with

Old phones for the cameras, one Pi 5 or a desktop as the head. The phones detect and ship crops; the head makes the government call for all of them. That is not a compromise — it is exactly how the code is already split, so it is the path with the least new work in it.

"I'll be the only camera in my city — won't police know exactly where I am?"

This is the right question to ask and it deserves a straight answer rather than a reassurance.

The street is published on purpose. The house is not. Those are different things and SparrowMap separates them deliberately, at different resolutions:

  • The camera's true coordinates never leave your machine. The database keeps them in an operator-only column; what is published is a separate jittered point, blurred by up to 60 metres.
  • What is published accurately is the watched span — the stretch of public road your lens covers, snapped to the road centreline. People are entitled to know where they are being recorded; that is the entire civic argument for the project.
  • The span is padded to a minimum of 80 metres, and the hub serves the span instead of a precise heading and reach. Both of those exist so nobody can back-project from the midpoint onto one or two houses.
  • Even the road lookup is coarse. The map query is snapped to a ~400 m grid before it leaves the machine, so the public API that resolves your street learns a neighbourhood, not an address. It runs once at enrolment and is cached.
  • Video never leaves at all. Recognition happens on your machine and only a small detection event is sent.

The part that is genuinely true, and is not solved by any of that

If you are the only node in a city, the published span is your street, give or take its minimum length. Jitter protects the house. Nothing in the system pretends to hide the road, because hiding the road would defeat the point of publishing at all.

So the honest framing is: a volunteer is choosing to publish that a camera watches a stretch of public road, and is protected from publishing which building it sits in. The thing that dilutes street-level attention is other cameras, which is a chicken-and-egg problem and worth saying out loud rather than engineering around.

One piece of history that should raise rather than lower confidence here: the jitter was defeated once, in this codebase. Node positions were published blurred while sightings were stored at the camera's true coordinates and served to anyone — so reading a single sighting handed you the exact camera. It was caught because the camera marker and its own sightings sat 57 m apart on the map and looked wrong. The first fix was also wrong. The current watched-span model is the third answer, and the reasoning is written out in full in road.py where it can be argued with.

Landmines worth knowing before you buy

  • Power supply first. A Pi 5 wants the 27 W USB-C supply. An under-voltage latch is the most common cause of mysterious slowness, and the benchmark reads that flag for exactly this reason.
  • Active cooling, not a bare board. Sustained CPU inference is the workload that throttles a Pi hardest. Run the soak before you believe a burst number.
  • Not a cheap SD card. A node writes crops continuously. NVMe if the board supports it, a decent A2 card otherwise.
  • Camera choice is decided by protocol, not brand. USB UVC, or an IP camera that genuinely speaks RTSP or ONVIF. Cloud-first cameras — the rebadged consumer ones especially — are unusable no matter how good the sensor is, because the stream never leaves the vendor.
  • A camera "works" only when it hands over a real frame. An open port and a plausible URL prove nothing; cameras answer on 554 and then refuse to stream, or return HTTP 200 with an HTML error page.
  • On Windows, use the MSMF backend, not DirectShow. Same camera, same resolution, six times the frame rate — DirectShow stays in an uncompressed mode and ignores the format request.
  • Wired network if you can. Wi-Fi is fine for uploads and flakier for something that must sit unattended for months.
  • Night without infrared is the wrong tool, not a hard problem. Plates are retroreflective, which is why every commercial reader has an IR illuminator. Test in daylight first.
